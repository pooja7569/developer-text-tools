# Version 1.1: test locally, then release

**Account integration update:** Optional Google sign-in and Stripe TEST billing
are now implemented behind explicit configuration, disabled in normal builds.
Use [BILLING_SETUP](BILLING_SETUP.md) for this separate setup. This guide still
describes the default free release and local Pro preview, not live subscriptions.

The polished UI uses a **Tool** selector rather than displaying all tool
buttons together. Input/output and current/baseline editors sit side by side
on screens at least 820px wide, and stack in the popup or side panel. Capture,
sample and clear actions are compact secondary controls. Optional sign-in and
test billing are under the expandable **Account** section.
Narrow panels no longer enforce a 320px page width. Below 341px, navigation
uses two columns. The compact Tool menu stays inside the panel instead of
opening an oversized native popup. Delete actions use a muted red outline;
their confirmation prompts are unchanged.
The toolbar popup has an explicit 480px width so Chrome does not shrink it
to narrow, character-wrapped content. This width applies only to the popup:
the side panel and full-page tab continue to fit their available space.
Editor actions use compact, content-width buttons with thin separators,
separate from privacy and draft guidance. Secondary actions retain visible
outlines instead of looking like plain text. The Tool label and 32px-high
picker share one row. This follows [Fluent 2 button hierarchy guidance](https://fluent2.microsoft.design/components/web/react/core/button/usage);
editor buttons retain visible keyboard focus and at least 32px-high click targets.
The extension has three actual Chrome views: **toolbar popup**, **full-page
tab**, and **side panel**. The header moves the current workspace between them:
popup -> full page -> popup, popup -> side panel -> popup, and full page <->
side panel. **Exit full page** and **Exit side panel** return to the actual
toolbar popup, not a small layout inside the previous container.

Inputs, baseline, output, selected tab/tool, comparison/inspection results,
presets, workspace selection, and local note drafts carry across. The destination
restores these values before the previous extension surface is closed; normal
webpage tabs are not closed. A full-page tab is reused if already available.
The original webpage is reactivated when leaving full page; if it was closed,
another webpage tab (or a normal new tab) hosts the returning popup/side panel.
Chrome uses separate documents internally; the shared draft makes them one
continuous workspace instead of blank, independent copies.
Exit side panel returns to the toolbar popup. If Chrome dismisses that popup
while closing the panel, it is reopened with the same restored draft.

Drafts are kept automatically in trusted `chrome.storage.session` **RAM only**,
separately for each Chrome window. They are not uploaded or written to disk,
and disappear when that window closes, Chrome restarts, or the extension reloads.
This temporary cache includes JWT input and generated output: use fabricated
tokens, and use **Clear drafts** when finished. Explicitly saved workspaces still
use local disk storage and exclude JWT input/generated output.
View controls briefly pause until the latest draft is in memory. A memory or
API failure is displayed, with retry controls; no silent blank-data fallback.
Seamless switching requires **Chrome 141+**, which provides native side-panel
closing. The popup keeps its 480px width; other views remain responsive.
Keep view transitions within the same Chrome window. If a full-page tab is
dragged into another window, switching pauses to prevent redirecting the wrong
window; keep the view open and save its workspace before reopening there.
Use the popup or side panel to capture text from another webpage; the full-page
extension tab itself is not a captureable HTTP/HTTPS page.

## 1. Build the normal free version

From PowerShell:

```powershell
Set-Location C:\Users\v-naresri\ChromeProject\frontend
npm.cmd run lint
npm.cmd test
npm.cmd run build
```

In Chrome 141 or newer:

1. Open `chrome://extensions`; enable **Developer mode**.
2. Reload the existing local extension, or **Load unpacked** and select
   `frontend\dist`. The local development ID is unchanged.
3. Open **DevToolBox**, click **Try sample**, then **Compare** and **Compare JSON**.
   Expect two changed values.
4. Under **Tools**, try **Validate / inspect**, expand the JSON tree, and search.
5. Pick JSON/YAML conversions, JWT decoding or Log to CSV from the **Tool**
   selector. Only the selected tool's actions are shown. The output is separate from your original input;
   copy it back manually when you want to transform it again.
6. For JWT testing use a fabricated test token, not a real credential.
7. Open **Workspaces**, enter a name, and **Save workspace**. Both current and
   baseline must be valid JSON. Close/reopen and load the saved workspace.
8. Try a second workspace: saving must fail without changing the first.
9. Export a workspace backup; check Chrome Downloads. Backups are unencrypted.
10. Enter unsaved JSON, format/convert it, and switch through all six directions:
    popup -> full page, full page -> side panel, side panel -> full page,
    full page -> popup, popup -> side panel, side panel -> popup.
    Expect identical values and only one extension surface after each switch.
    No manual Save/Load is needed to move these temporary drafts.
    Saving after another window changes disk storage must still show a
    revision conflict; refresh before saving. Drafts remain intact.
11. Narrow the side panel and check all four tabs with Account expanded:
    content must wrap without a horizontal page scrollbar. Open the Tool menu;
    its text and options must fit the panel. Use arrows, Home/End and Enter to
    choose a tool, Escape to cancel, and Tab to move on. Changing tools must
    preserve input; choosing the current tool again must preserve output.

Selection capture needs a toolbar click on the target tab to grant temporary
`activeTab` access. After switching tabs, reopen the toolbar popup on the new
page before capturing from the side panel.

All new local tools work without Django. Existing notes and local CSV still
need the backend described in [README](README.md). The side panel survives
popup closure. Temporary drafts survive view switches and popup reopening,
but not closing the Chrome window, restarting Chrome, or reloading the extension.

## 2. Test advanced features without charging anyone

```powershell
Set-Location C:\Users\v-naresri\ChromeProject\frontend
npm.cmd run build:pro-preview
```

Load `frontend\dist-pro-preview` unpacked. It displays a development-preview
notice. It shares the local development identity when loaded in the same
profile; export existing workspaces before replacing a loaded build.
Do not run two separately installed builds and assume their data is synced.

- Save two named workspaces; close/reopen to verify persistence.
- Ignore `/meta/requestId` in the sample comparison: expect only the status change.
- Download the full change report from **Output**.
- Select JSON files in **Compare** for a local batch report.
- Under **Generate**, create TypeScript and Pydantic v2 output. Review aliases,
  optional fields, unions, and precision warnings.
- For multiple examples, use valid JSON documents separated by a line
  containing `---`. Missing fields become optional. Dates/enums are not guessed.
- Redaction matches comma-separated field names recursively, case-insensitively.
  Check the preview yourself: unmatched secrets may remain. Original input
  and saved workspaces are unchanged.
- Save presets with the workspace. Switching back to free preserves viewing,
  export and deletion of all existing workspaces, but disables advanced actions.
  Updating its JSON in free mode preserves existing locked advanced presets.

The preview is selected by the Vite **mode**, not storage or an environment
variable. `VITE_PRO_PREVIEW=true` cannot enable it in a free/cloud build.
Never upload `dist-pro-preview` to the store.

## Limits and storage

- Individual JSON/YAML/token input: 256 KiB UTF-8; JSON depth 64 and 10,000 values.
- YAML: JSON-compatible mappings/sequences/scalars only; unsupported tags,
  aliases, duplicate keys, non-string mapping keys, and non-finite numbers fail.
- Compare: object key order ignored, array positions compared; missing differs
  from null. Ignore rules are exact JSON pointers, not regex or wildcard rules.
- Preview batch: 1-20 files, 256 KiB each, 2 MiB total; all validate before output.
- Generation: up to 20 examples, 256 KiB combined; inference is not a schema guarantee.
- Workspaces: free 1; preview 50; 4 MiB total encoded storage/backup size.
- Import is additive: existing IDs are skipped, not overwritten. Invalid or
  over-limit imports fail entirely. Confirmation is required.
- Workspaces use a versioned storage key separate from the old SQLite notes.
  A worker serializes mutations; revision checks prevent stale-window overwrites.
- Corrupt data is not silently reset. **Export workspace backup** can export
  raw stored data even when it fails validation, for manual recovery.
- No tokens, outputs, selected files, or drafts are automatically persisted.

No new Render deployment is required for the new local features.
The existing stateless CSV endpoint remains unchanged.


The cloud bundle has version **1.1.0**, no local-development key, no backend
notes UI, and no enabled Pro preview. Chrome Web Store keeps the existing
published identity when you upload to the existing item.

1. Test the cloud bundle unpacked first. Its temporary unpacked ID differs
   from the published ID; allow that exact test origin in Render only while
   testing CSV. Keep the published origin allowed.
2. Render Free may sleep; wake the greeting endpoint and retry CSV after it is
   ready if the extension's ten-second timeout expires.
3. Publish the updated [privacy policy](PRIVACY.md) and verify its public URL.
4. In the Web Store dashboard, open the **existing DevToolBox item**
   `nlipiinielfeldfkniccognjaaihajkd`, upload the zip, and update the listing
   using [STORE_LISTING](STORE_LISTING.md).
5. Explain the new `storage` and `sidePanel` permissions accurately.
6. Include original screenshots of free features, not preview-only tools.
7. Verify the installed store update preserves existing data and CSV works.

Do not create another Web Store listing, publish the local/preview build, or
promise purchasable subscriptions. Publishing to the Chrome Web Store is a
separate manual step; building or opening a GitHub pull request does not submit
the extension.
